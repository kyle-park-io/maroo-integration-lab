## 2. 왜 이 세 트랙인가

트랙마다 앞머리(이름, 주제, 대상, 예시)는 빌더가 끌리는 문제에서 출발하고, 뒷머리(primitive, 최소 연동 요건, 증명, 심사, 무효 사례)는 Maroo 기능에서 출발합니다. 사람을 모으는 주제와 내용을 지키는 기준을 한 문서 안에서 나눠 맡긴 구조입니다.

주제는 지금 Maroo 테스트넷에서 비어 있는 자리에 맞췄습니다.

| 비어 있는 자리 | 테스트넷에서 확인한 것 | 채우는 트랙 |
| --- | --- | --- |
| 외부 개발자가 Privacy를 끝까지 쓴 사례 | Privacy 프리컴파일로 간 최근 tx 50건이 모두 성공했지만 마지막 tx는 2026-09-21 04:40 UTC입니다. 외부 개발자가 유효한 증명을 만들 회로 산출물과 차폐 상태 조회 경로는 공개되지 않았습니다 `[Live Testnet]` | 1 |
| 에이전트 신원 등록 | IdentityRegistry의 다음 agentId는 79이고, 레지스트리로 간 마지막 tx는 2026-09-06 18:15 UTC입니다 `[Live Testnet]` | 2 |
| 기관과 사용자가 참고할 원화 결제 레퍼런스 | 전역 정책이 KYC 없는 계정에 건당 200만 OKRW, 24시간 1,000만 OKRW 한도를 두고 있지만, 이 규칙 위에서 자격별 한도를 설계한 공개 앱을 찾지 못했습니다 `[Live Testnet]` | 3 |

- 근거: [기술 근거 기록](evidence/live/grounding-20260925T194211Z.json), 재현 `pnpm c:grounding`
- 트랙 2는 피지컬 AI 개발자를 부르는 갈래(기기가 결제하는 에이전트)를 둡니다. 로봇과 기기를 다루는 개발자는 크립토 밖에서 모이는 큰 빌더 집단이고, 이 갈래는 하드웨어 없이 기기 시뮬레이터로도 같은 요건을 채우게 해서 참가 규모가 보드 수에 묶이지 않게 했습니다.

## 3. 세 트랙이 서로 겹치지 않게 나눈 기준

| 질문 | 트랙 1 | 트랙 2 | 트랙 3 |
| --- | --- | --- | --- |
| 누가 돈을 보내나 | 기업(사람이 승인한 지급) | 에이전트나 기기(사람이 위임한 지급) | 사용자와 가맹점 |
| 무엇을 지키나 | 금액과 거래 관계의 비공개 | 위임한 한도 | 자격에 따른 한도와 권한 |
| PCL이 판정하는 것 | Privacy 호출자와 제품 컨트랙트 호출자 | 에이전트 지갑의 전송 한도 | 앱이 발급한 증명의 유무, 폐기, 한도 |
| 심사에서 가장 큰 배점 | 프라이버시 경계와 감사 설계 | 한도 거부를 받은 뒤 에이전트의 동작 | 자격 모델과 거부 사유 처리 |

한 프로젝트가 두 트랙 요건을 모두 채우면 참가자가 한 트랙을 골라 제출하고, 다른 트랙 요건은 심사에서 가산 요소로만 봅니다.

## 4. 모든 트랙에 공통인 규칙

### 증거 라벨

제출물은 실행 결과마다 `[Live Testnet]`, `[Local]`, `[Simulation]`, `[Docs Only]`를 붙입니다. Clairveil 로컬에서 만든 증명과 tx는 Maroo 테스트넷 호환성의 증거가 되지 못하므로, 두 환경의 결과를 한 흐름의 성공으로 합쳐 적으면 해당 요건을 채우지 못한 것으로 봅니다.

### 공통 제출 자료

| 자료 | 내용 |
| --- | --- |
| 공개 레포 | 실행 명령이 있는 README, 버전 고정(Node, SDK, Clairveil 커밋) |
| `evidence.json` | 요건마다 네트워크, chain ID, 호출 대상, tx 해시, 탐색기 링크, 예상 결과, 실제 결과, 라벨, 실행 시각. 형식은 [트랙 1의 증거 요건](tracks/1-private-settlement.md#23-테스트넷-증거-요건) |
| 데모 영상 | 3분 안팎. 성공 경로와 거부 경로를 모두 보여 줌 |
| 한계 기록 | 동작하지 않은 것, 로컬로 대신한 것, 누락된 선행 조건 |

### 공통 무효 사례

- 조회 함수만 부르거나, 로고와 이름만 쓰거나, 문서에서 기능을 언급만 한 제출
- Maroo 호출을 목(mock)으로 대신하고 라벨 없이 실제 호출처럼 보여 준 제출
- 로컬 결과를 테스트넷 결과로 적은 제출
- 일부러 잘못된 증명을 보내 되돌려진 tx를 Privacy 연동 성공으로 적은 제출
- 다른 체인에서 만든 결과를 Maroo 결과로 적은 제출

### 공통 심사 흐름

1. 자동 판정: 심사용 스크립트가 `evidence.json`의 tx 해시를 테스트넷 RPC로 조회해 요건별로 통과 여부를 표시합니다. 영수증 상태, 호출 대상, OKRW 이동, PCL 정책 바인딩(`IPcl.contractPolicies`), 거부 사유를 확인합니다.
2. 재현 확인: 심사위원이 README의 명령으로 로컬 경로를 실행합니다. 15분 안에 첫 결과가 나오지 않으면 재현성 점수를 깎습니다.
3. 리뷰: 데모와 코드를 보고 트랙별 배점표로 채점합니다.
4. 결선: 상위 팀이 5분 발표와 질의응답을 합니다.
